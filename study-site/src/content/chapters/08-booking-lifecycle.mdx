A slot is not a separate entity — it is a bookings row in the `pending` state with no customer attached. The lifecycle has just three meaningful transitions, and each one is guarded.

## The key endpoint: `POST /bookings/{id}/book`

```python
@router.post("/{booking_id}/book", response_model=BookingResponse)
def book_slot(booking_id, db, current_user=Depends(require_customer)):
    booking = get_booking_or_404(booking_id, db)
    result = db.execute(
        update(Booking).where(
            Booking.id == booking.id,
            Booking.status == BookingStatus.PENDING,
            Booking.customer_id.is_(None),
        ).values(customer_id=current_user.id, status=BookingStatus.CONFIRMED)
    )
    if result.rowcount == 0:
        raise HTTPException(status_code=409, detail="Slot is no longer available")
```

Three things happen in one shot: the id is re-checked, the status is confirmed still pending, and the customer_id is confirmed still NULL. Chapter 9 unpacks the concurrency story behind `rowcount == 0`.

## Listing is role-filtered

`GET /bookings` branches per role before querying:
- **Admin** — no filter, sees all.
- **Provider** — `WHERE provider_id = current_user.id`.
- **Customer** — either your own bookings, or (when `?status=pending`) only slots with `customer_id IS NULL`. That lets customers discover available slots without ever seeing another customer's booking.

## PUT and DELETE are restricted to open slots

Both require `owner_or_admin` and both guard: `status == pending AND customer_id IS NULL`. Once a booking is claimed (`confirmed`), the provider cannot reschedule, and the customer cannot throw it away — the row is now a real booking with consequences.

<Callout kind="note" title="No cancellations today">
  <code>cancelled</code> exists in the enum but no endpoint sets it. The only way a booking disappears physically is DELETE — and only when it's still an open slot. This is a deliberate scope decision, not an oversight.
</Callout>

## Complete transitions are state-gated

`POST /bookings/{id}/complete` uses the same conditional UPDATE pattern:

```python
result = db.execute(
    update(Booking).where(
        Booking.id == booking.id,
        Booking.status == BookingStatus.CONFIRMED,
        Booking.customer_id.is_not(None),
    ).values(status=BookingStatus.COMPLETED)
)
if result.rowcount == 0:
    raise HTTPException(status_code=409, detail="Booking is not in a state that can be completed")
```

A pending slot can't be completed — only a confirmed booking with a customer. This preserves the review requirement: only completed bookings are reviewable, and the state change is atomic.
